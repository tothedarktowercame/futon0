### HydraDB — https://hydradb.com/
- **Problem:** Agents that recall by vector similarity alone lose relationships and time ordering between facts, so they need a store that keeps facts as a graph with timestamps and can be searched by both meaning and connection.
- **How:** Two layers. The open core is a distributed graph database in Rust: S3-compatible object storage (SlateDB) is the durable source of truth, query nodes and indexer nodes scale separately, traversal uses SuiteSparse GraphBLAS, and clients speak OpenCypher over Neo4j Bolt 5.x or an HTTPS JSON/NDJSON API. On top sits a hosted "memory" service (hybrid keyword+semantic retrieval, LLM extraction of entities into the graph, connectors to Confluence/Drive etc.) reached through a CLI, an MCP server and plugins for Claude Code, Codex, Cursor, OpenCode, LangChain, CrewAI and others.
- **Get:** Core `hydra-db/hydradb` is AGPL-3.0 (GitHub license field, LICENSE badge). The CLI, MCP server and plugins are Apache-2.0. Hosted: Ship $25/mo + $6 per 1M overage, Scale $299/mo, Enterprise custom (pricing from homepage; card/free-trial terms unverified).
- **Build:** The graph core is fully public (Rust, ~1.6 MB repo, ~13k stars, with architecture.md). The memory layer (ingest → inference → hybrid retrieval) appears to be hosted-only; its API is documented in detail through the MCP/CLI READMEs, so a clone is feasible as a few thousand lines on any graph+vector store.
- **Use:** The graph DB self-hosts on Linux with S3-compatible storage (MinIO would do) and a Rust 1.91+ toolchain. The agent-memory features (`query`/`ingest` with inference) appear to need the hosted API key (unverified whether the OSS includes them).
- **Verbs:** MCP tools: `hydradb_query`, `hydradb_ingest`, `hydradb_list`, `hydradb_inspect`, `hydradb_delete`, `hydradb_status`, `hydradb_subgraph`, `hydradb_feedback`, `hydradb_graph_query`, `hydradb_graph_collections`, `hydradb_graph_admin`. Older aliases: `search`, `store`, `ingest_conversation`, `list_memories`, `list_sources`, `fetch_content`, `delete_memory`. CLI: `login`, `logout`, `doctor`, `config show|set`, `query`, `feedback`, `ingest`, `list`, `inspect`, `relations`, `subgraph`, `verify`, `delete`, `database`, `graph`, `connectors`. Query modes `fast`/`thinking`; feedback ratings `positive`/`negative`/`neutral` with `ground-truth-answer`. Two corpora: `memory` vs `knowledge`. Ingest separates `observation_date` (when true) from storage time. Taglines: store, recall, search.
- **Search seeds:** "agent memory knowledge graph open source"; "object storage native graph database cypher"; "temporal knowledge graph agent memory" (Graphiti/Zep); "GraphBLAS graph database" (FalkorDB, which hydra-db has forked); "MCP memory server graph".

### ApertureData (ApertureDB, aperture-nexus) — https://github.com/aperture-data/ (product: https://www.aperturedata.io/)
- **Problem:** Images, video, documents, their embeddings and their metadata/relations usually sit in three separate systems (blob store, vector DB, graph/SQL DB); this puts them in one database queried in one request.
- **How:** ApertureDB is a closed-source server (it grew out of Intel's VDMS; the Python client still carries "Copyright 2017 Intel Corporation") with a JSON command language over TCP: an array of commands such as `FindEntity` → `FindImage` with constraints, connections and on-the-fly image ops. Newer `aperture-nexus` (Python) is an agent-memory layer on top: commits carry a who/what/when/why/how Context, get embedded (CLIP or a text model), and are linked in the graph with lineage back to the originating interaction.
- **Get:** Server: closed; the Docker image `aperturedata/aperturedb-community` is "licensed for evaluation and development only, with no production use" (nexus README). Cloud: 30-day free trial, then Basic $0.33/h, Standard $1.29/h, Premium $4.00/h, Custom. Clients: `aperturedb-python` MIT (LICENSE file; GitHub shows NOASSERTION because of the dual copyright header); `aperture-nexus` MIT; `workflows` MIT.
- **Build:** The command language is public and the client is open, so the API can be reimplemented; the server (multimodal storage, vector indexes, graph engine) is not. Its open ancestor IntelLabs/vdms is the nearest build-your-own starting point. aperture-nexus itself is small (Python, 19 stars).
- **Use:** On Linux via Docker Compose with the community image, for development only; production self-hosting needs a commercial licence. Nexus needs Python 3.10+, ApertureDB server 0.19.14+ and, for semantic search, an embedding model.
- **Verbs:** Query-language commands (from client source): `AddEntity`, `FindEntity`, `DeleteEntity`, `AddConnection`, `FindConnection`, `DeleteConnection`, `AddImage`, `FindImage`, `UpdateImage`, `DeleteImage`, `AddVideo`, `FindVideo`, `DeleteVideo`, `AddClip`, `DeleteClip`, `DeleteFrame`, `AddBlob`, `FindBlob`, `DeleteBlob`, `AddBoundingBox`, `FindBoundingBox`, `DeleteBoundingBox`, `AddPolygon`, `FindPolygon`, `DeletePolygon`, `AddDescriptorSet`, `FindDescriptorSet`, `DeleteDescriptorSet`, `AddDescriptor`, `FindDescriptor`, `CreateIndex`, `RemoveIndex`, `GetIndexes`, `GetSchema`, `GetStatus`, `UpdateUser` (the pattern is CRUD verb × object type). Nexus: `commit`, `process_and_commit`, `search`, `authenticate`, `create_principal`; CLI `adb-nexus init`, `adb-nexus validate`. Nexus's own loop vocabulary: Information → (with Context) commit → Memory → hardens into Knowledge; "update or discard beliefs".
- **Search seeds:** "multimodal database vector graph images video"; "VDMS visual data management system"; "unified vector graph blob store"; "agent memory lineage provenance knowledge graph"; "multimodal RAG database open source".

### Immersive Commons — https://www.immersivecommons.com/
- **Problem:** A physical members' space for AI builders (Floor 10, Frontier Tower, 995 Market St, SF) needs to run events, membership, equipment lending, room booking and member-to-member introductions, and wants members' own agents to do that on their behalf rather than through a web UI.
- **How:** Not a product: a community floor whose website is an agent-first API. One per-user bearer token (`agt_...`, minted by a human-approved device-code flow) reaches ~278 tools over REST (OpenAPI 3.1 at /openapi.json), MCP (/api/mcp) and A2A (/.well-known/agent-card.json); 83 OAuth-style scopes over five tiers (public, ft-member, ai-floor, ic-member, operator); optional RFC 9421 signed requests; x402 USDC payments and per-member Base/Solana receive-only wallets; an LLM gateway key ("IC Key") to Z.ai GLM and Nebius open-weight models. Submitted text is sanitised and wrapped in a `message_safe_render` envelope against prompt injection.
- **Get:** Free. /pricing.md: "nothing to buy on this site"; all membership tiers $0, operator-approved; API rate-limited per token, not metered. Physical tower membership is sold separately by Frontier Tower. No source code or licence published (none found in llms-full.txt, mcp.json or openapi.json).
- **Build:** The interface is fully specified in public (655 KB OpenAPI spec, 145 KB llms-full.txt, MCP manifest with tool list and scopes), so the agent surface of a community space could be cloned; the backend is not published. It is a large surface: weeks of work to replicate in full.
- **Use:** Nothing to self-host; it is a service for one building. Ten-plus public tools (THE SIGNAL newsletter, news feed, presentations archive, forms, scheduling availability) work with no token from any MCP client.

### ZeroDB (AINative Studio) — https://ainative.studio/products/zerodb
- **Problem:** An agent developer has to stand up and wire together a vector store, a document/table store, file storage, an event queue and a memory layer; this offers all of them behind one hosted API and MCP server.
- **How:** Hosted backend (FastAPI; pgvector HNSW, NoSQL-style tables, S3-compatible files, event streams, serverless functions) plus a memory layer with working/episodic/semantic tiers, "consolidation" and "decay scoring", and a graph layer the site describes as RDF with SPARQL 1.1, OWL reasoning and bi-temporal as-of queries (those graph claims are unverified; I saw them only on the marketing page). `zerodb-local` mirrors the cloud API locally: Lite mode is SQLite + FAISS + in-process BAAI/bge-small embeddings; Full mode is Docker Compose with Postgres+pgvector, Qdrant, MinIO and RedPanda.
- **Get:** Cloud: 3-day trial, then Hobbyist $5/mo; dedicated Postgres add-ons $15–$249/mo. `AINative-Studio/zerodb-local` is MIT (GitHub license field), as are the SDKs and most MCP packages; the 83-tool `ainative-zerodb-mcp-server` has no licence field (unverified/none).
- **Build:** Yes. zerodb-local is public, MIT, ~1.2 MB, and claims to mirror "all 128 ZeroDB Cloud endpoints". The concept is a thin facade over standard parts (Postgres, FAISS/Qdrant, MinIO, a queue). Caution: the org has ~100 repos, nearly all 0 stars, many "drop-in replacement for X backed by ZeroDB" packages pushed on the same day (Supabase, Neon, Firebase, BullMQ, Celery, mem0, ChromaDB, Trigger.dev, QStash), and MCP tools named `zerodb_quantum_*`. - **Use:** Yes: `pip install zerodb-local[lite]` and `zerodb serve` on Linux with Python 3.11+, no Docker and no key (per README); Full mode needs Docker and ≥4 GB RAM. Optional `--cloud-key` for bidirectional sync.

### TypeSafe AI — System One models, Jev — https://typesafe.ai/blog/introducing-system-one-models-and-jev
- **Problem:** Code that needs a quick judgement from an LLM (classify this, is this true, rate this) gets slow, costly free text that has to be parsed and carries no usable probability; this returns typed answers with calibrated probabilities in tens to hundreds of milliseconds.
- **How:** A hosted classifier-style model (Jev; docs mention `jev-1.13`, default `jev-latest`) behind one endpoint, `POST https://api.typesafe.ai/v1/systemone` (plus `/v1/models`). Each request holds a `state` (unstructured context) and a map of named questions of three types, all evaluated in parallel and in isolation. The blog claims a new architecture with a "parallel sampler" (all outputs at once rather than token by token) and an RL method, "RLCD" (RL for Calibrated Decisions). No paper or weights were found. The org's fork of LLaDA (a diffusion LLM) hints at the sampler design; that is unverified inference.
- **Get:** Hosted only; early access opened 2026-10-09 via console.typesafe.ai. Price per the blog: input $0.042 per M tokens, output free. Free tier unverified. SDKs `typesafe-sdk-python` and `typesafe-sdk-js` are MIT; `skills` (agent skill) is MIT; `system-one-adapter-python` ("Drop-in TypeSafeClient replacement backed by LLM APIs") is MIT (GitHub license fields via `gh api`).
- **Build:** The interface is small and fully documented, and TypeSafe itself ships an MIT adapter that implements it on top of ordinary LLM APIs. A local version (logprob-based choice/score/yes-no with calibration) is a few hundred lines; the speed and calibration claims depend on their model, which is closed. Their numbers (193.6x faster, 444.6x cheaper, "0% hallucination") are vendor-reported, and the 0% only means answers always match the schema.
- **Use:** Jev itself cannot be self-hosted. **But the System One wire protocol now can be:** SGLang (Apache-2.0) added a "System One compatible" `POST /v1/systemone` route on 2026-09-25 (PR #41208, on top of a generic `/v1/decisions` route, #40992) that answers by scoring single-token answer labels, "without generation", on any model. On 2026-10-09 it added support (PR #42721) for Cloudflare's open **Clef** (Qwen3.8-27B) and **Clef-Flash** (Qwen3.5-9B) decision models (Hugging Face `Cloudflare/clef`, `Cloudflare/clef-flash`, both Apache-2.0, published 2026-09-30). These are a Qwen backbone plus a "joint schema head" that returns one logit per option of every question in a single prefill. Per the PR, TypeSafe SDK clients "work unchanged" by changing the base URL. So a self-hosted Jev substitute exists if you have a GPU (Clef-Flash 9B is the smaller one); CPU-only boxes cannot run it. The MIT adapter also runs against any LLM API.
